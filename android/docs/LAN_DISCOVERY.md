# Wi-Fi device discovery

The Wi-Fi screen offers an explicitly started, authorization-gated check of the directly connected private IPv4 subnet. It accepts only a /24 to /30 network, excludes this phone and the network/broadcast addresses, and checks at most 253 other addresses. The app attempts TCP connections to ports 80, 443, 22, 445, and 8080 through the Wi-Fi network's socket factory. It uses at most 16 workers and a 350 ms timeout per connection, with a 60-second overall limit. The same run also performs a bounded service browse. Results stay in memory; leaving Wi-Fi or the app stops the operation.

Atlas also browses nine common DNS-SD/mDNS service types for six seconds on the selected Wi-Fi network. A resolved service within the bounded subnet can add an address even when the TCP ports do not respond. It can provide an advertised service name and, on Android 16 or later, a resolved mDNS hostname. Atlas labels roles from the advertised service type: printing, media receiver, file sharing, workstation, remote shell, or web service. These are **service claims**, not verified hardware types or ownership. Atlas does not infer a printer or computer solely from an open TCP port.

If Android reports a default IPv4 gateway within the selected subnet, Atlas labels that address as a **network gateway (Android route)**. This is a network role, not a claim about the hardware model. TCP transport errors and mDNS query/resolution failures are shown as warnings; timeouts and refused connections remain non-responses, not proof of absence.

A device with no listening service on the checked ports and no supported service advertisement, a firewall, client isolation, another subnet, or IPv6-only connectivity may be absent. No result does not mean no other devices exist. Atlas does not query router DHCP client lists, attempt reverse DNS, or send data to a cloud service. On Android 12, Wi-Fi-bound NSD is unavailable; TCP discovery still works and the UI reports incomplete name discovery. Names and roles are shown with their source, and results stay in memory.

`INTERNET` and `ACCESS_NETWORK_STATE` support this tool. `CHANGE_WIFI_MULTICAST_STATE` supports a six-second multicast lock on Android 13 devices that need it for mDNS reception. On Android 17 with Atlas targeting API 37, `ACCESS_LOCAL_NETWORK` must also be granted at runtime. The app requests it from the Wi-Fi screen. The permission is shared with the selected-host TCP tool. Android guidance: https://developer.android.com/privacy-and-security/local-network-permission

Unit tests cover subnet bounds, successful-connect reporting, error propagation, service evidence merging, and name sanitization. The Pixel checks below cover one network and controlled mDNS advertisement. Additional physical validation remains needed for other routers, client isolation, reconnection, scan duration, battery impact, and Android 12-16 behavior. A successful build does not verify those behaviors.

## Pixel validation, 2026-11-05

On a Pixel 10 Pro XL running API 37, an authorized run on `192.168.1.42/24` completed 253/253 address checks. It observed only the default gateway at `192.168.1.1`, with successful TCP connections on 80, 443, and 445. The PC at `192.168.1.2` was listening on 445 locally, but a connection from the Pixel timed out and two ICMP requests received no reply. The cause of that filtering was not established. The router returned no PTR name for the PC, and a service browse without controlled advertising returned zero in-subnet service observations.

For a controlled positive test, the PC temporarily advertised `Atlas Test PC` as `_http._tcp` using `dns-sd` on an unserved test port. Atlas observed the PC at `192.168.1.2` with mDNS hostname `PS5killer` and the service name, despite filtered TCP. Android supplied the raw type `._http._tcp`, which exposed a role-mapping defect. After normalization and an in-place app update, a repeat run completed 253/253 and labeled the PC's advertised role **Web service**. The advertisement was stopped; a fresh run returned one observed address and zero in-subnet service observations. These are synthetic-advertisement results, not proof of broad real-device name coverage.

Revoking `ACCESS_LOCAL_NETWORK` on the Pixel disabled the Find devices action; the permission was restored through the app. Stopping a live run left stable partial progress at 176/253 addresses. Battery impact, multi-router behavior, and Android 12-16 behavior were not measured. The observed result set is therefore validated for this Pixel and network only.

On the final pre-deadline build, a normal run completed all 253 addresses with one gateway result and zero in-subnet service observations. UI polling observed it still running about 35 seconds after start and complete before 57 seconds; exact duration was not measured. A 60-second overall limit was then added to keep a slow run bounded. A focused Pixel instrumented test used a fake slow probe and a 50 ms test limit; it passed with `Time limit reached; partial results` and no scan traffic. The real 60-second duration was not forced on the home network.

The negative unit test for `SecurityException` initially failed: worker failures inside a supervisor scope yielded an empty successful scan. The worker scope now propagates failures, and the regression test passes. Individual socket I/O errors are counted and shown as partial-result warnings. The connection selector now waits for an eligible private Wi-Fi IPv4 address rather than accepting the first Wi-Fi callback.

After the final name-sanitization edit, the offline debug unit tests, debug and unsigned release assemblies, and debug lint completed successfully. The rebuilt debug APK was installed in place on the Pixel with local-network permission granted. The bounded timeout instrumented test passed again against that installed build (`OK (1 test)`, 0.439 seconds). The test package was removed afterward, and Atlas was returned to the foreground. This final test exercises a fake slow probe and short injected limit; it does not replace a real-network soak test.

## Release boundary

This feature reports bounded observations, not a complete client inventory or a verified device model. The API 37 Pixel/home-LAN path has positive and negative physical evidence above. A general Android release still needs Android 12-16 device checks, more than one router/network configuration, battery/long-run measurements, and an app release signing decision. The assembled release APK is currently unsigned; Atlas's version remains `0.7.0-preview`. Those are release holds, not evidence that the feature's Pixel path failed.
